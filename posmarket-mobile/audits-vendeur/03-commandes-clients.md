# Commandes & Clients — spec mobile (parité web)

> Référence = les pages vendeur web `/orders` et `/customers`, rendues à largeur mobile (< 768 px).
> Fichiers : `src/views/OrdersView.tsx` (708 lignes), `src/views/CustomersView.tsx` (692 lignes), `src/app/(app)/orders/page.tsx`, `src/app/(app)/customers/page.tsx`, `src/components/ConfirmationModal.tsx`, `src/components/PhoneInput.tsx`, `src/components/buyer/Modal.tsx`, `src/hooks/useSupabaseData.ts` (`fetchOrderItems`), `src/app/actions/orders.ts`, `src/app/actions/customers.ts`.
> Règle de lecture : classe sans variante = mobile ; `hidden md:*` / `hidden sm:*` = desktop → EXCLU ; `md:hidden` = mobile → INCLUS ; `text-[9px] md:text-[11px]` → 9 px.
> Chrome (coquille vendeur, web mobile) : `BottomNav` `md:hidden` fixe en bas (items ≥ 52 px, libellés 9 px, safe-area) et `main` avec `pb-20` (80 px) ; les toasts placés à `bottom-[88px]` passent juste au-dessus. Les deux pages s'ouvrent depuis les items « Commandes » (ShoppingBag) et « Clients » (Users) de cette barre.
> Couleurs : brand `#F56B2A`, brand-soft `#FFF3ED`, orange-50 `#FFF7ED` ; vert `green-500` `#22C55E`, ambre `amber-500` `#F59E0B`, bleu `blue-500` `#3B82F6`, gris `gray-50` `#F9FAFB`, `gray-100` `#F3F4F6`, `gray-400` `#9CA3AF`, `gray-500` `#6B7280`, `gray-900` `#111827`, rouge `red-600` `#DC2626`, jaune `yellow-500` `#EAB308`.
> Aucun bloc « impression » ni « WhatsApp » n'existe dans ces deux vues (la seule action WhatsApp, bouton `Phone` vert de la colonne Actions clients, est desktop → EXCLUE).
> Rien ne doit être inventé : tout élément absent de cette spec ne doit pas apparaître dans l'app.

## Page /orders

### Données attendues (props + fournisseur)

- `src/app/(app)/orders/page.tsx` (serveur) : session Supabase (`supabase.auth.getSession()`) ; si pas de session → `null` ; `getEffectiveStoreId(supabase, session)` ; si aucune boutique → `<NoStoreFound />` ; sinon `loadOrdersForStore(storeId)` (cache 20 s, tag `orders:{storeId}` → `fetchFormattedOrders`, **100 dernières commandes**, tri `date` desc, chaque commande jointe à ses `order_items` + produit) et `fetchStoreData(storeId, undefined, { products: false, customers: false, invoices: false })` → `{ store }` ; puis `getPermissionsForUser(supabase, session.user.id, storeId)` → `{ permissions, role }`.
- Props de la vue :
  - `orders: Order[]` : `id`, `date` (ISO), `status` (`'PENDING' | 'READY' | 'COMPLETED'` + valeurs libres), `type` (`'IN_STORE' | 'PICKUP'`), `paymentMethod` (affiché tel quel), `subtotal`, `total`, `discountAmount`, `promoCode`, `customer?` (`id`, `name`, `email`, `phone`, `address`, `totalSpent`, `ordersCount`), `items[]` (`product` : `id`, `name`, `price`, `image`, `storeId`, `businessType`, `mainCategory`, `unit` ; `quantity`, `unitPrice`, `total`, `variantLabel`, `variantSku`).
  - `currentStoreId?: string` : indispensable (tous les appels serveur le passent).
  - `permissions`, `userRole`, `store` : transmis par la page mais **jamais lus** par la vue (aucun garde-fou visuel).
- Chargement interne à la vue : `fetchOrderItems(orderId)` (items détaillés) ; repli immédiat sur `selectedOrder.items` si la requête échoue.
- Mobile RN : pas de server actions ni du polyfill `@/supabase` (il exécute des server actions). Prévoir des routes API équivalentes exposées via `src/api/client.ts` (cookie de session + `X-PosMarket-Client: mobile-app` déjà gérés). Aujourd'hui seules `api/marketplace/seller/auth/login` et `seller/bootstrap` existent côté vendeur : les routes commandes sont à créer.

### Actions & données utilisées (imports @/app/actions/*, supabase, fetch)

- `@/app/actions/orders` : `getOrdersAction(storeId, offset = 0, limit = 10, search = '', filterStatus = 'all')` → `{ success, orders, hasMore, total, error? }` (LIKE sur id / code promo / nom / téléphone client, tri date desc, statut filtré si ≠ `ALL`) ; `updateOrderStatusAction(orderId, status)` ; `deleteOrderAction(id)` ; `bulkUpdateOrderStatusAction(orderIds, status)` ; `bulkDeleteOrdersAction(ids)` — toutes renvoient `{ success, error? }` et vérifient `requireStoreAccess` / `requireOrderAccess` (erreur type `ACCES_REFUSE` renvoyée dans `error`, affichée en toast).
- `../hooks/useSupabaseData` → `fetchOrderItems(orderId)` : `order_items.select('*')` puis `products.select('id, name, price, image, business_type, main_category, unit, wholesale_price, wholesale_min_qty, wholesale_tiers')`, fusion par `product_id` (prix numériques, `wholesaleTiers` normalisés).
- `@/supabase` : **polyfill** (pas de `@supabase/supabase-js`) — chaque requête passe par les server actions `execQuery` / `execRpc` (`@/app/actions/sql`) et l'auth par `@/app/actions/session`. Inutilisable en RN → prévoir des routes API.
- `@/components/RouterPolyfill` (`useRouter`) pour `router.refresh()` après chaque mutation.
- Utilitaires : `formatCurrency` (`@/utils`), `getEffectiveWholesaleUnitPrice` (`@/utils/wholesale`).
- Aucun `fetch` HTTP dans la vue ; aucune impression, aucun message WhatsApp, aucun appel téléphonique déclenché.
- Effets : recherche debouncée 500 ms (relancée aussi au montage) ; resynchronisation sur `initialOrders` ; sélection vidée à chaque changement de filtre.

### Permissions

- La vue reçoit `permissions` et `userRole` mais ne les lit **jamais** : aucun bouton n'est masqué selon le rôle sur cette page (mise à jour de statut, suppression unitaire et groupée visibles pour tous).
- Le contrôle est **côté serveur** uniquement : `requireStoreAccess` (boutique) et `requireOrderAccess` (chaque commande, y compris pour les actions groupées) ; en cas de refus, l'`error` est affichée en toast et aucune donnée n'est modifiée.
- `store` (nom, settings) est transmis mais inutilisé.

## Points ambigus / à vérifier

1. **Pastilles de verticale `/orders`** : les classes actives sont construites dynamiquement (`bg-${color}-500 border-${color}-500`) ; elles ne sont générées que parce que `bg-orange-500` / `bg-gray-500` / `bg-yellow-500` / `border-*-500` apparaissent statiquement ailleurs (DashboardView, InventoryView). En RN, coder en dur : `gray-500` `#6B7280`, `orange-500` `#F97316`, `yellow-500` `#EAB308`.
2. **Aucun garde-fou de permission dans `OrdersView`** : le bouton d'avancement de statut et les suppressions sont visibles pour tout rôle ; seul le serveur refuse. À reproduire tel quel ou à trancher.
3. **Compteurs d'onglets** : calculés sur le lot chargé (`localOrders`), pas sur le `total` serveur ; après filtrage par statut, « Toutes (N) » et les autres compteurs reflètent uniquement les commandes renvoyées par ce filtre.
4. **`hasMore` initial** : `orders.length === 10` / `customers.length === 10` à l'état initial, puis `>= 10` après resynchronisation ; comme la page fournit jusqu'à 100 lignes d'un coup, le bouton « Voir plus » peut apparaître alors que tout est déjà chargé (et relancer un offset à 100).
5. **Recherche relancée au montage** : le debounce de 500 ms se déclenche aussi sans saisie → la liste initiale est remplacée par la 1re page serveur (10) peu après l'ouverture.
6. **Segment « Inactifs » jamais alimenté** : `lastOrderDate` n'est fourni par aucune requête ; le compteur reste « Inactifs (0) » et le filtre vide la liste.
7. **Seuil VIP en dur** : 500 000 FCFA de `totalSpent` cumulé ; non configurable.
8. **Boutons inertes** : `Filter` (recherche commandes) et « Appeler » (clients) n'ont aucun `onClick` ; le chevron des lignes clients et le chevron des commandes sont décoratifs ; le glissement de la poignée de la feuille détail n'est pas implémenté (fermeture par flèche ou « Fermer »).
9. **Feuille détail** : `h-[85vh]` sans marge basse ni gestion du clavier ; le bouton `X` desktop est remplacé par `ArrowLeft` en mobile ; la corbeille n'a pas de texte.
10. **Statuts hors PENDING/READY/COMPLETED** : libellé « Payée » + badge gris ; le bouton du pied affiche « Livrée » gris **mais reste cliquable** (désactivé seulement si statut `COMPLETED`).
11. **`paymentMethod`** affiché brut (valeurs de base type `ESPECES`), sans traduction ni badge ; visible uniquement en desktop dans la liste, mais dans la feuille détail en mobile.
12. **Modale client** : seulement nom + téléphone (pas d'e-mail ni d'adresse malgré le type `Customer`) ; en édition, l'objet fusionné conserve les champs non modifiés mais l'action ne réécrit que `name`, `email`, `phone`, `address`, `totalSpent`, `ordersCount`.
13. **Toasts** : positionnés à 88 px du bas (au-dessus de la `BottomNav`) et durée fixe de 3 s ; le toast clients n'a pas d'icône, celui des commandes en a une.
14. **Données mobile** : aucune route API vendeur n'existe pour commandes/clients (seuls `seller/auth/login` et `seller/bootstrap`) ; il faut créer les équivalents REST des 9 actions utilisées (5 commandes, 4 clients) + le détail des items, en conservant les garde-fous d'accès.
